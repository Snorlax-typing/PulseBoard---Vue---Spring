一、pom.xml 整体结构速览
================================================================================

一个 pom.xml 主要回答四个问题：

  1. 我是谁？          -> groupId / artifactId / version（项目坐标）
  2. 我继承谁？        -> <parent>（父 POM）
  3. 我依赖什么？      -> <dependencies>（依赖列表）
  4. 我怎么构建？      -> <build>（插件）

你的 pom.xml 对应关系：

  [我是谁]
    groupId    = com.example          （组织/团队标识，通常是倒写域名）
    artifactId = demo                 （项目/模块名）
    version    = 0.0.1-SNAPSHOT       （版本号，SNAPSHOT 表示开发中的快照版）

  [我继承谁]
    parent = spring-boot-starter-parent:4.1.1

  [我依赖什么]
    - spring-boot-starter-webmvc       （编译期，写 Web 应用用）
    - spring-boot-starter-webmvc-test  （仅测试期，scope=test）

  [我怎么构建]
    - spring-boot-maven-plugin         （打包成可执行 jar、支持 spring-boot:run）

二、父 POM：spring-boot-starter-parent 是什么？
================================================================================

<parent>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-parent</artifactId>
    <version>4.1.1</version>
    <relativePath/>
</parent>

它相当于 Spring Boot 官方提供的"标准地基"。继承它之后，你免费获得：

  1. 依赖版本统一管理
     - 父 POM（及其父级 spring-boot-dependencies）已经规定好了
       几千个常用第三方库的"经过测试、互相兼容"的版本。
     - 所以你在 <dependencies> 里写 starter 时【不用写 <version>】，
       版本由父 POM 统一裁定，避免版本冲突。
     - 例：你只写了 spring-boot-starter-webmvc，没写版本，
       自动就是 4.1.1；它带进来的 Tomcat、Jackson 等版本也都被锁定。

  2. 默认的编译配置
     - Java 编译版本（你用 java.version=17 覆盖/指定）
     - 源码编码 UTF-8
     - 合理的插件配置

  3. 资源过滤、打包规则
     - application.properties / application.yml 的占位符处理
     - 配合 spring-boot-maven-plugin 打出可执行的 fat jar（胖包）

  一句话：它把"该用什么版本、怎么编译、怎么打包"这些繁琐的默认值
          都替你定好了，你只需要关心"我要什么功能"。

三、核心概念：什么是 Starter（启动器）？
================================================================================

3.1 为什么需要 Starter
--------------------------------------------------------------------------------
在没有 Starter 的时代，搭建一个 Spring Web 项目要手动：
  - 引入 spring-core / spring-context / spring-web / spring-webmvc
  - 引入 Tomcat
  - 引入 JSON 库（Jackson）
  - 引入日志库（slf4j + logback）
  - 还要自己保证这些版本彼此兼容、不冲突
  - 再手动写一堆 XML 配置
非常繁琐、容易出错。

Starter 就是来解决这个问题的。

3.2 Starter 的定义
--------------------------------------------------------------------------------
Starter 是一组"打包好的依赖集合描述符"（本质还是一个普通的 Maven 依赖，
只是它自己不怎么写代码，主要靠 <dependencies> 把一堆相关 jar 聚合进来）。

它遵循"约定优于配置"：
    你只需要声明【我要某一类功能】，
    Starter 就把实现该功能所需的全部依赖一次性、版本兼容地拉进来。

命名规律：
    官方 Starter：spring-boot-starter-xxx
        例：spring-boot-starter-webmvc（Web MVC）、-data-jpa（数据库）、
            -security（安全）、-redis（缓存）……
    第三方/新版本中也有更细粒度的模块命名（如带 -test、-tomcat 后缀）。

3.3 你的 spring-boot-starter-webmvc 到底拉进了什么？
--------------------------------------------------------------------------------
下面是用 mvn dependency:tree 得到的真实依赖树（缩进表示"被谁依赖"）：

com.example:demo
└─ spring-boot-starter-webmvc:4.1.1
   │
   ├─ spring-boot-starter:4.1.1                 （所有 starter 的公共底座）
   │   ├─ spring-boot-starter-logging:4.1.1     （默认日志方案）
   │   │   ├─ logback-classic 1.5.38            （日志实现，含 logback-core）
   │   │   ├─ log4j-to-slf4j 2.25.5             （把 log4j API 桥接到 slf4j）
   │   │   └─ jul-to-slf4j 2.0.18              （把 java.util.logging 桥接）
   │   ├─ jakarta.annotation-api 3.0.0          （@Resource 等注解）
   │   └─ snakeyaml 2.6                         （解析 YAML 配置文件）
   │
   ├─ spring-boot-starter-jackson:4.1.1         （JSON 序列化/反序列化）
   │   └─ jackson-databind 3.1.5
   │       ├─ jackson-annotations 2.21
   │       └─ jackson-core 3.1.5
   │
   ├─ spring-boot-starter-tomcat:4.1.1          （内置 Web 服务器）
   │   ├─ tomcat-embed-core 11.0.24             （Tomcat 核心）
   │   ├─ tomcat-embed-el 11.0.24               （表达式语言支持）
   │   ├─ tomcat-embed-websocket 11.0.24        （WebSocket 支持）
   │   └─ spring-boot-tomcat 4.1.1
   │
   └─ Spring 框架核心（Web MVC 实现）
       ├─ spring-context 7.0.9                  （容器、上下文）
       ├─ spring-web 7.0.9                      （Web 基础能力）
       ├─ spring-webmvc 7.0.9                   （Spring MVC 核心）
       ├─ spring-beans 7.0.9                    （Bean 定义与管理）
       ├─ spring-aop 7.0.9                      （面向切面）
       └─ spring-expression 7.0.9               （SpEL 表达式）

这些依赖可以分成四大功能块：

  +----------------+----------------------------------------------+
  | 功能块          | 对应 jar                                      |
  +----------------+----------------------------------------------+
  | Web 服务器      | tomcat-embed-core / el / websocket           |
  | Spring MVC     | spring-web / spring-webmvc / spring-aop      |
  | JSON 处理       | jackson-databind / core / annotations        |
  | 日志            | logback / slf4j 桥接                          |
  | 容器/配置       | spring-context / spring-beans / snakeyaml    |
  +----------------+----------------------------------------------+

这就解释了你之前的现象：
  - 为什么 mvn spring-boot:run 之后直接有一个 Web 服务跑在 8080？
      -> 因为内置了 Tomcat（tomcat-embed-core），不需要你单独装 Tomcat。
  - 为什么 Controller 里 return 一个对象/字符串会自动变成 JSON？
      -> 因为有 Jackson，Spring MVC 自动做了消息转换。
  - 为什么控制台自动有格式化日志？
      -> 因为有 logback + slf4j，且 Spring Boot 配好了默认日志格式。

3.4 测试 starter：spring-boot-starter-webmvc-test
--------------------------------------------------------------------------------
  <scope>test</scope> 表示它只在测试代码（src/test）和测试运行时可用，
  不会被打进最终的生产 jar。

  它聚合了一整套测试工具：
    - JUnit Jupiter 6.0.3       （测试框架：@Test 等）
    - Mockito 5.23.0            （模拟对象/Mock，含 mockito-junit-jupiter）
    - AssertJ 3.27.7            （流式断言，assertThat(...).isEqualTo(...)）
    - Hamcrest 3.0              （匹配器）
    - JSONPath / JSONAssert     （断言 JSON 内容）
    - spring-test（spring-core 等）（Spring 测试上下文支持）
    - byte-buddy / objenesis    （Mockito 底层动态生成 Mock 对象用）

  好处：写完业务代码，不用自己逐个找测试库，starter 一次配齐。

四、核心概念：什么是自动配置（Auto-Configuration）？
================================================================================

4.1 问题：依赖有了，谁来"组装"它们？
--------------------------------------------------------------------------------
Starter 解决的是"把需要的 jar 放进 classpath"。
但光有 jar 还不够，还需要有人把这些组件"装配"起来，例如：
  - 启动 Tomcat 并监听端口
  - 注册 DispatcherServlet（Spring MVC 的总前端控制器）
  - 配置好 JSON 转换器
  - 把你写的 @Controller / @Service 注册成容器里的 Bean
  - 读 application.properties 里的配置

传统 Spring 要手写大量 XML / Java 配置来完成这些。
Spring Boot 用【自动配置】把这一步也自动化了。

4.2 自动配置的定义
================================================================================
自动配置 = Spring Boot 根据【classpath 上有哪些 jar】 + 【你已有的配置/
Bean】，自动帮你创建并装配好所需的组件（Bean），让应用"开箱即用"。

核心思想：
    "只要你引入了某个能力的 starter，我就猜测你大概率需要它的默认配置，
     并自动帮你配好；如果你自己定义了，就以你的为准。"

4.3 触发入口：@SpringBootApplication
--------------------------------------------------------------------------------
你的主类：

    @SpringBootApplication
    public class DemoApplication {
        public static void main(String[] args) {
            SpringApplication.run(DemoApplication.class, args);
        }
    }

@SpringBootApplication 是一个组合注解，主要包含三个关键注解：

    @SpringBootConfiguration   标明这是一个配置类（本质是 @Configuration）
    @EnableAutoConfiguration   开启自动配置（核心！）
    @ComponentScan             扫描本类所在包及子包中的组件

其中 @EnableAutoConfiguration 会去加载一系列自动配置类（Spring Boot 4 中
通过 AutoConfiguration.imports 机制登记）。这些自动配置类都带有条件判断，
满足条件才生效。

4.4 自动配置是怎么"按需生效"的？—— 条件装配
--------------------------------------------------------------------------------
自动配置类不是无脑全部生效，而是用一系列"条件注解"来判断：

  @ConditionalOnClass(某类)
      当 classpath 上【存在】指定的类时才生效。
      例：classpath 上有 Tomcat 的类（因为你引入了 starter-tomcat），
          才会自动配置内嵌 Tomcat。

  @ConditionalOnMissingBean(某类型)
      当容器里【还没有】该类型的 Bean 时才创建默认的。
      这是"你不写我就用默认，你写了就用你的"的关键。
      例：你自己定义了一个 ObjectMapper，Spring Boot 就不创建默认的。

  @ConditionalOnProperty(某配置项)
      当配置文件中某属性为特定值时才生效。
      例：spring.mvc.hiddenmethod.filter.enabled=true 才注册某过滤器。

  其他：@ConditionalOnWebApplication、@ConditionalOnBean 等。

判断逻辑可以概括为：

        classpath 有这个类？
           |            |
          是            否 -> 不配置（你没引入这个能力）
           v
   你已经自己定义了这个 Bean？
        |            |
       是            否
       v             v
   用你自己的      创建默认的（@ConditionalOnMissingBean）

4.5 自动配置在你项目里的具体表现
--------------------------------------------------------------------------------
  - 你引入了 spring-boot-starter-webmvc
        -> classpath 出现 Tomcat、Spring MVC、Jackson 的类
        -> 对应的 ServletWebServerFactoryAutoConfiguration、
           DispatcherServletAutoConfiguration、JacksonAutoConfiguration 等
           判定条件满足，自动生效
        -> 于是：内嵌 Tomcat 启动（默认 8080）、DispatcherServlet 注册、
           JSON 消息转换器就绪
        -> 你全程没写任何服务器/框架配置。

  - 你写了 @RestController 的 HelloController
        -> @ComponentScan 扫描到它，注册成 Bean
        -> DispatcherServlet 自动把 "/" 映射到 hello() 方法
        -> 返回值经 Jackson 转换写回响应

4.6 配置的"默认值"如何被覆盖？
--------------------------------------------------------------------------------
自动配置提供了大量合理默认值（如端口默认 8080）。你可以通过
application.properties / application.yml 覆盖，例如：

    server.port=8081              改端口
    spring.application.name=demo  应用名（你目前只配了这一项）

Spring Boot 会把这些属性绑定到配置类上（@ConfigurationProperties），
实现"默认值 + 你的覆盖"的组合。

4.7 如何查看自动配置生效情况？（排障常用）
--------------------------------------------------------------------------------
启动时加 --debug（或在 application.properties 写 debug=true）：

    mvn spring-boot:run -Dspring-boot.run.arguments=--debug

报告会输出：
    Positive matches：条件满足、已生效的自动配置
    Negative matches：条件不满足、未生效的自动配置
    Exclusions：被排除的配置
当某个组件"为什么没自动配好"时，看这个报告最直接。

五、Starter 与自动配置的关系（重点区分）
================================================================================

  Starter（依赖层面）
    解决：把实现某功能所需的 jar 一次性、版本兼容地放进 classpath。
    本质：Maven 依赖聚合（pom）。
    回答："我需要哪些库？"

  自动配置（运行时装配层面）
    解决：根据 classpath 内容和你的配置，自动创建、组装 Bean。
    本质：一批带条件注解的 @Configuration 类。
    回答："这些库怎么被组装起来、默认怎么配？"

  两者配合：
    你引入 starter -> 相关类出现在 classpath
                  -> 自动配置的条件被满足
                  -> 组件自动装配，开箱即用。

  类比：
    Starter  = 你买了一整套"宜家家具包"（零件齐全、型号匹配）
    自动配置 = 附赠的"自动组装机器人"，看到零件就按默认图纸装好；
               你若想自己摆（自定义 Bean/配置），它就听你的。

六、构建插件：spring-boot-maven-plugin
================================================================================

<build>
  <plugins>
    <plugin>
      <groupId>org.springframework.boot</groupId>
      <artifactId>spring-boot-maven-plugin</artifactId>
    </plugin>
  </plugins>
</build>

作用：
  1. 支持 mvn spring-boot:run   直接编译并运行应用
  2. mvn package 时把应用打成【可执行的 fat jar】
     - fat jar 里包含你的代码 + 所有第三方依赖 + 内嵌 Tomcat
     - 部署时只需：java -jar demo-0.0.1-SNAPSHOT.jar
     - 不需要在目标机器上额外安装 Tomcat。

七、整体工作流程串讲（从 pom 到服务跑起来）
================================================================================

  1. 你在 pom.xml 声明 spring-boot-starter-webmvc
  2. Maven 借助父 POM 裁定兼容版本，把 Tomcat、Spring MVC、Jackson、
     日志等全部依赖拉进 classpath（Starter 依赖聚合）
  3. 执行 mvn spring-boot:run，main 方法调用 SpringApplication.run
  4. @SpringBootApplication 触发：
       - 组件扫描：发现并注册你的 HelloController
       - 自动配置：依据 classpath 条件，自动配好 Tomcat、
         DispatcherServlet、JSON 转换器、日志等
  5. 内嵌 Tomcat 启动，默认监听 8080
  6. 浏览器访问 http://localhost:8080/
       -> DispatcherServlet 找到 "/" 映射 -> 调用 hello()
       -> 返回字符串经 Jackson 写回 -> 页面显示内容
  7. 你只写了极少量代码，其余全部由"Starter + 自动配置"完成。


================================================================================
八、关键结论速记
================================================================================

  1. spring-boot-starter-parent 是"标准地基"：统一版本、默认编译/打包配置，
     所以 starter 依赖不用写 <version>。

  2. Starter 是"依赖打包"：声明功能，自动拉齐该功能所需的全部兼容 jar。
     - webmvc starter = 内嵌 Tomcat + Spring MVC + Jackson + 日志。

  3. 自动配置是"智能装配"：依据 classpath（@ConditionalOnClass）和
     你是否已自定义（@ConditionalOnMissingBean），按需创建默认 Bean。

  4. @SpringBootApplication = 配置类 + 开启自动配置 + 组件扫描。

  5. 默认值可用 application.properties 覆盖；--debug 可查看自动配置报告。

  6. Starter 管"有哪些库"，自动配置管"怎么组装"，二者共同实现"开箱即用"。

  7. spring-boot-maven-plugin 让你能 spring-boot:run，并打出可执行 fat jar。
